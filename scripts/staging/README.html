Free, isolated staging tests

This runs PostgreSQL, PostgREST, the actual social/conversation API modules and k6 on your PC. It does not load production environment files, call paid AI providers, or send traffic to ricomates.si. Docker's internal network blocks outbound traffic. Images are pinned to the tested digests.

Run

From the repository root with Docker running:

docker compose -f scripts/staging/compose.yaml --profile tests pull
npm run test:staging:setup
docker compose -f scripts/staging/compose.yaml exec -T app node /app/scripts/staging/verify.cjs
npm run test:staging:load
npm run test:staging:restore
docker compose -f scripts/staging/compose.yaml stop

Setup creates one million tiny synthetic profiles, 10,000 posts and 100,000 reactions. It is idempotent for fixtures. Load levels are 10, 50 and 100 virtual users with 3–5 second pauses, each held for 90 seconds with ramps. Tests cover feed reads, pagination, stories, likes and saves. No test posts to a real user's account.

Interpretation

The harness uses a synthetic Clerk adapter only inside this standalone test process. It is not part of Next.js, and the whole staging folder is excluded from Vercel deployments. These tests measure API/database behavior, not Vercel autoscaling, real Clerk authentication, geography, browser rendering, voice, meeting bots, object-storage throughput or paid model capacity. A million stored synthetic profiles is not a million simultaneous users.

Results and the synthetic backup are in scripts/staging/results/, which is ignored by Git and excluded from deployment. The recovery drill restores into a disposable database, compares all row fingerprints and verifies the 16 SQL functions before removing only that restored fixture database. The staging volume is retained; the final stop command frees its running CPU/RAM without deleting data.

Operations and security

AI_GENERATION_DISABLED=true blocks model generation, while privacy deletion requests remain available. Production defaults still use the established shared provider limits. The new rico_operation logs contain status, elapsed time and service category only. All failures and slow calls are logged; fast successes are sampled at 1%.

SOCIAL_OBJECT_STORAGE_ENABLED=true stores new social JPEGs in the private rico-social-photos Supabase bucket. Images are limited to 256 KiB, private links expire after 60 seconds, and signing is bounded and cached. Existing inline images remain readable. Normal object deletion is immediate; failed/interrupted operations leave durable cleanup tasks for the existing keepalive job, after a one-hour grace period.

protect-data-backup.ps1 encrypts a single-row Supabase application-data CSV export with Windows DPAPI and verifies the decrypt round trip. It is an application-data snapshot, not a full Supabase/Clerk disaster-recovery backup. Preserve the Windows profile needed to decrypt it; keep backups out of Git and deployment artifacts. There is no scheduled production backup or automatic retention deletion in this setup.
